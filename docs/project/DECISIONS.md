# Architecture and product decisions

| Date | Decision | Reason | Canon impact | Reversible |
|---|---|---|---|---|
| 2026-07-18 | Use project-local Supabase ports 54329 (API), 54339 (database), 54349 (Studio), 54359 (Mailpit) and 54369 (Analytics). | Port preflight showed these ports free and AGENTS.md requires isolation from sibling projects. | No canon change; isolates local services. | Yes |
| 2026-07-18 | Pin Supabase CLI 2.109.1 as a project-local devDependency. | Reproducible Docker image selection and migrations without global system changes. | No product impact. | Yes |
| 2026-07-18 | Give `authenticated` only table `SELECT` under RLS and route all application mutations through narrow RPCs. | Earlier tables had overly broad DML grants while later tables lacked usable read grants. | Enforces server validation, least privilege and auditability. | Yes, via migration. |
| 2026-07-18 | Keep the first dashboard on server-owned fixture data until staff Auth and RLS are connected. | The visual foundation can be validated without weakening the production authorization boundary. | Temporary implementation state; release remains blocked. | Yes |
| 2026-07-18 | Keep parent secrets in `private` schema and expose only narrow server-only RPC wrappers. | The private schema must not be accessed through the Data API. | Implements the prescribed secret boundary. | Yes |
| 2026-07-18 | Derive the versioned 256-bit QR bearer value with HMAC-SHA-256 from the per-environment random pepper and order/version, while storing only its SHA-256 hash. | This keeps the QR opaque and free of PII, permits rotation, and allows the same seasonal QR to be rendered again without storing plaintext. | Implements the canon's 256-bit bearer, hash-only storage and `PARENT_TOKEN_PEPPER` contract. | Yes, before production issuance. |
| 2026-07-18 | Require the bearer token again on fulfilment commit instead of trusting a prior lookup result. | A scan result can become stale through rotation, refund or concurrent use. | Enforces the required live token recheck inside the transaction. | Yes. |
| 2026-07-18 | Enforce staff AAL2 in middleware, server context and the database role helper. | A UI-only MFA check would leave RPC and stale-session bypasses possible. The database helper raises `42501` when AAL2 or an active profile is missing. | Implements mandatory staff MFA and immediate blocking of inactive profiles. | Yes, via migration. |
| 2026-07-18 | Expose only `public`, `graphql_public` and `app` through the local Data API; keep `private` unexposed. | User-scoped server clients invoke guarded `app` RPCs, while parent secrets remain behind narrow public service-role RPC wrappers. | Preserves the canon's server/client and secret boundary. | Yes. |
| 2026-07-18 | Serve the backoffice dashboard through one AAL2- and role-guarded aggregate RPC with a strict Zod response contract. | Metrics, recent orders and audit activity must share one consistent database snapshot and must fail closed on unexpected data. The response omits member e-mail and audit metadata. | Replaces the temporary visual fixture without widening access or exposing unnecessary personal data. | Yes, via a forward migration and contract version. |
| 2026-07-18 | Keep active-season shell context in a separate minimal staff RPC. | `uitgifte` needs the current season in the shared shell but must not receive backoffice metrics, members or audit activity. | Preserves least privilege across the three staff surfaces. | Yes. |
| 2026-07-18 | Use self-cleaning fictitious browser fixtures only inside the dashboard regression script. | Production-like states are needed for screenshot and responsive validation, while persistent sample users or records could be mistaken for operational data. | No product data is seeded; test accounts, MFA factors and records are removed in `finally`. | Yes. |
| 2026-07-18 | Split the member overview into a PII-minimal list RPC and an explicit member-detail RPC. | Searchable tables do not need parent e-mail or linkage data; details do. Separate strict contracts reduce accidental bulk disclosure and keep `uitgifte` excluded from both RPCs. | Implements least privilege while preserving the canonieke right-hand detail panel. | Yes, via forward migration and contract version. |
| 2026-07-18 | Execute all member filtering and pagination inside the AAL2-guarded database RPC. | Client-side filtering would require overfetching and could produce inconsistent totals. Server-side filters cover name, relation number, team, payment, order, article, size and fulfilment. | Implements the canonieke operational filters without widening browser trust. | Yes. |
| 2026-07-18 | Convert validated Sportlink domain rows to an explicit snake_case database payload before RPC calls. | TypeScript domain naming and PostgreSQL record keys differ; an explicit adapter makes the boundary testable and prevents nullable record fields at runtime. | No product behavior change; completes reliable preview and transactional commit. | Yes. |
| 2026-07-18 | Store a size snapshot on every order line and make the size of a used variant immutable. | Historical orders and fulfilments must not change when the active catalog evolves. | Implements canonical season history without hard-deleting used variants. | Yes, via forward migration. |
| 2026-07-18 | Standalone QR revocation leaves zero active tokens; an explicit later rotation creates the next version. | Revocation must immediately block scanning, while reactivation must remain deliberate, reasoned and auditable. Resend never rotates. | Resolves the canon ambiguity with the safest least-privilege behavior. | Yes, before production issuance. |
| 2026-07-18 | Treat fulfilment correction as a whole-order-line administrative reversal. `ready_for_pickup` restores the fulfilled reservation; `backorder` releases it. | The canon does not define partial correction within a quantity greater than one or a separate returns workflow. | Keeps the MVP atomic and inventory-consistent without inventing returns/exchanges. | Yes, with a later canonical partial-quantity model. |
| 2026-07-18 | Keep an all-cancelled paid order at the existing derived status `Afgerond`. | The canon defines no additional status for this edge case and forbids invented order states. | Preserves the exact canonical order-status vocabulary. | Yes, via a documented future canon revision. |
| 2026-07-18 | Accept QR hashes and trusted payment mutations only through service-role RPCs after an AAL2/RBAC route guard, and grant service_role only schema USAGE plus explicit function EXECUTE. | Browser-callable SECURITY DEFINER functions could otherwise bypass route validation or choose secret material. | Strengthens the prescribed server/client secret boundary without granting service_role table access through the app. | Yes, via forward migration. |
| 2026-07-18 | Keep the OTP code in a fixed, non-editable SendGrid block outside the durable e-mail queue. | The canon requires a verification template but its closed shortcode list has no OTP shortcode. Persisting plaintext OTP in a job would violate the hash-only secret boundary. | Safest resolution of the canon ambiguity: six-digit OTP remains direct, single-purpose and never durable; surrounding verification content cannot be edited. | Yes, after an explicit canon shortcode decision. |
| 2026-07-18 | Store editable e-mail sources as validated plain text and render escaped HTML server-side. | This supports accessible multipart mail while excluding scripts, arbitrary expressions, forms and unsanitized HTML. | Implements the closed shortcode allowlist without adding a free-form template language. | Yes. |
| 2026-07-18 | Bind bulk confirmation to a ten-minute HMAC preview token and immutable per-job template snapshots. | Confirmation must preserve the reviewed template, exact unique order selection and batch identity even when a template is edited later. | Implements fictional previews, batches up to 2,000 orders and replay-safe per-order jobs. | Yes. |
| 2026-07-18 | Do not automatically reclaim e-mail jobs left in `processing`. | SendGrid Mail Send has no end-to-end idempotency guarantee; automatic reclaim after provider acceptance but before local completion could send twice. | Fails operationally closed: such jobs require manual investigation rather than risking duplicate member mail. | Yes, if a provider reconciliation mechanism is introduced. |
| 2026-07-18 | Use the classic Mollie form webhook and always fetch the current payment object server-side. | The webhook body contains only an identifier and is not trusted as payment evidence; redirect pages never mutate payment state. | Implements the canon's webhook-first Payments API boundary without adopting beta or Orders APIs. | Yes. |
| 2026-07-18 | Treat any observed refund amount as fail-closed `refunded`, revoke active QR access, and preserve fulfilment history. | Partial refund behavior is outside the MVP and must not leave issue rights active while financial state is ambiguous. | Applies the strictest safe interpretation; refund initiation remains outside scope. | Yes, after a future partial-refund canon. |
| 2026-07-18 | Derive the parent-visible effective payment state by prioritizing `paid`, then `refunded`, then `duplicate_paid`, then the latest attempt. | A later duplicate attempt must not hide the primary paid state or its active QR; refund of the primary payment must still block it. | Keeps multi-attempt provider history compatible with the one-order payment truth. | Yes, via forward migration. |
| 2026-07-18 | Keep club name and logo immutable as `Duindorp SV` and the supplied original logo; settings may change only operational contact, pickup, season, amounts, staff and provider switches. | The higher-priority design canon forbids generic branding and logo reinterpretation. | Resolves the lower-level settings wording without introducing multi-tenant or mutable branding. | Only after an explicit canon revision. |
| 2026-07-18 | Require both the environment flag and the beheerder-controlled database switch before Mollie or SendGrid can create outgoing provider traffic. | Runtime configuration must remain a hard emergency ceiling, while operations needs an audited immediate pause control. | Adds no new feature flag; it implements two independent safety layers for the two canonical providers. | Yes. |
| 2026-07-18 | Protect browser mutations with exact same-origin validation plus Fetch Metadata and the `X-Duindorp-CSRF: same-origin` proof header. | HttpOnly cookies alone do not prove same-origin intent; the custom non-simple header and origin/host checks make cross-site form and fetch submissions fail closed. | Strengthens the required server-side authorization boundary without adding client trust. | Yes. |
| 2026-07-18 | Generate XLSX exports server-side with pinned ExcelJS and neutralize spreadsheet formulas in every text cell for CSV and XLSX. | The MVP requires native Excel output, while member-controlled fields must not become spreadsheet commands. | Implements the canonical export formats within the modular monolith. | Yes. |
| 2026-07-18 | Use prefixed repository Actions configuration and two repository-level self-hosted runners until protected GitHub Environments are available. | The private repository remains on GitHub Free, while staging and production must deploy to an isolated VPS without touching Castivo. Separate users, labels, paths and services reduce cross-project impact; a release-author/dispatcher split adds a temporary four-eyes gate. | Deployment remains canon-compatible but carries a documented weaker workflow-administration boundary until a plan upgrade. | Yes; migrate the same unprefixed contract to protected Environments after upgrade. |
